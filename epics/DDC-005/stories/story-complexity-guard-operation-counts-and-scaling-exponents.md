## Description

A wall-clock limit ("scan in ≤ 60 s") catches a slow machine as readily as a slow algorithm, and it misses a quadratic step until the input is big enough. This story catches a quadratic step by its shape, in two complementary ways:

1. **Cost counters (deterministic, in the fast gate).** The core counts the work its hot paths do. The counters measure cost, not call sites. A loop that calls a cheap function n times and a function that reads a directory of n entries both show up.
   - `dir_entries_read`: every entry returned by a directory read, wherever it happens in `ddc-core`. Counting inside the two `DirReader` implementations (`scan/reader.rs`, `sys/bulk.rs`) covers the walker, `exec/preflight.rs` and `report/recheck.rs`. One lazy `stats::read_dir` adapter covers the direct `fs::read_dir` sites: `report/project.rs` (`last_activity`), `rules/matcher.rs`, `rules/classify.rs`, `rules/toolchain.rs`, `exec/delete.rs`, `disk/` and `agents/`. This is the counter that catches `aa64c83` step 2.
   - `claim_lookups`: comparisons made while matching claims to findings, and while looking a path up among the findings in `report/contents.rs`. This does **not** catch a verbatim restore of step 1: the pre-`aa64c83` code was a bare `findings.iter().any(|f| f.path == o.path)`, which reads nothing, allocates nothing and moves no counter. It catches step 1 only when the comparison is counted, as the runbook's "Adding a counter" requires. No counter design catches an uncounted comparison loop. Measured at L on `mixed` (Technical Notes): a restored step 1 shows in the user-time fit of `make scaling` (1.89 against 0.98 on the fixed code), not in the user + system slope (1.10), which the system time flattens.
   - `rule_match_attempts`: every call of the rule matcher. This counts calls, not cost: the cost is in the child lookups (`has_child`, `has_child_dir`), each a scan of a listing that `dir_entries_read` already counted. It is linear while the visitor calls the matchers once per directory read.
   - `ancestor_checks`: every step up the ancestors while looking for a project root, and every prefix check against excludes.
   - `marker_checks`: every check of a claim or a user-data entry against the keep markers, split from `ancestor_checks` so the markers × claims product is never diluted by the linear project-root walk.
   - `allocations` and `bytes_allocated`: a counting `#[global_allocator]` wrapper, active only under the feature.

   A test runs the same profile at n and 2n entries and checks each counter's ratio, where r is the growth of the manifest's entries, not of its findings: findings are planted in proportion to the entries, and the difference falls inside ε. It fails if a counter grows faster than its declared bound: linear for most, n·log n where it is justified and written next to the counter. A quadratic step multiplies by 4 instead of 2. That is visible on small trees, independent of the machine, and never flaky.
2. **Scaling slopes (CPU time, user time and memory, measured on the reference machine).** The harness times scan and report (`scan`), plan (`clean-dry-run`) and the after-clean recheck (`clean-items`) at four sizes, n, 2n, 4n and 8n, where 8n is the tier: 12 500 to 100 000 for M, 125 000 to 10⁶ for L. It fits the log-log slope of CPU time (user + system), of user time alone and of peak memory, and reports above 1.2. This catches costs that no counter sees: syscalls, locks, cache misses, and possibly an uncounted comparison loop. CPU is judged on the local slope between 4n and 8n, only where the median CPU at 4n is at least 1 s (a spread of δ ms on a median of m ms moves the local slope by about δ / (m · ln 2): the tens of milliseconds a scan of a few hundred wobbles by move it by more than 0.1, so below the floor it is recorded and not judged); the full fit is recorded for information (the constant base flattens it). User time is judged on the fit through all four sizes, on any machine, where its median at 4n is at least 250 ms: it has almost no base to flatten the fit, and on a busy machine the system time hides a quadratic user-time step in the sum. With no base, the fit reaches 1.2 only when a quadratic part is about a quarter of the user time at 4n (two fifths at 8n), where the local slope would at 15%; a constant base raises that share (with a base of a quarter of the linear part at n, to a third at 4n). The local user slope is recorded beside the fit (`user_slope`), so a fit well under it shows a base. Peak memory is judged above the profile's base from `bench/load-limits.tsv` (`rss_base_bytes`, about 11 MB), and only at L: at M most profiles add a few hundred bytes per entry to that base, so the raw slope is near 0 whatever the algorithm.

## Decomposition

- [x] A `stats` module in `ddc-core`. Counters are relaxed atomics behind a cargo feature `op-stats`, which is not a default feature; without it every call compiles to nothing. Each counter is declared with its bound (`Linear`, `NLogN`) and a one-line reason. Tests read counters as deltas around the measured scan. nextest runs each test in its own process, so counters never leak between tests and the ratio tests can run in parallel (the existing `load` test group). They run only through nextest; `make check` is an alias of `gate-fast`, so no gate path runs them under plain `cargo test`. The ratio test is compiled with or without the feature and fails when every counter reads 0, so dropping `op-stats` from the Makefile's `FEATURES` fails the gate instead of silently removing the guard. The whole gate (golden outputs, `load_cli`, every unit test) runs on the counting-allocator build; only `release-check`, `scripts/build-dist.sh`, `scripts/build-app.sh` and `make load` run the shipped allocator (and, outside the gate, `make test` and the release builds of `bench-test`). (Commits `ae070e5`, `469b72a`; the zero-counter assertion in `d9ad787`.)
- [x] `op-stats` and the memory story's `dhat-heap` both install a `#[global_allocator]`: a `compile_error!` refuses both at once. (`crates/ddc-core/src/heap.rs`, commit `fa7cff7`.)
- [x] The counters above at their sites. (`ae070e5`, `469b72a`; `marker_checks` in `d9ad787`.)
- [x] A sweep of the comparison loops over findings, claims and keep markers in `report/`, `rules/` and `exec/preflight.rs`: each one is counted, or is listed in the runbook with why it is bounded (for example `report/contents.rs`, `walked.iter().find` once per user-data folder). A heap profile or a samply recording cannot establish this: a comparison loop allocates nothing. A structure test cannot either: no grep tells a loop over the findings from a loop over a fixed catalog. - [x] Fast-gate test, in process (library calls, no harness needed), folded into `crates/ddc-loadgen/tests/profiles.rs`: the S tree of 10 000 entries that `check` already builds and scans is the 2n point, so only an n = 5 000 tree is built extra, for every profile (about +55 000 entries for the group, half more work). 10 000 is the most a marked temporary folder may hold on macOS (`TEMP_MAX`), and n is not lower because of the fixed home scaffold, measured by generating each profile at 1 entry: 708 entries in `system-root`, 728 in `mixed`, 636 in `users`, 846 in `deep-path-max`, under 150 elsewhere. r is taken on all entries, but counters that grow with the planted items grow (2n − F)/(n − F) times; at 2 500 → 10 000 they grew 5–8 times for 4 times the entries and failed falsely (`system-root` preflight `ancestor_checks` 224 → 1 536, `mixed` 181 → 924). The small tree is scanned and preflighted once before it is measured, so the process's one-time allocations (the catalog, lazy statics) are paid before either point; the large tree is measured after its verifying scan; the small tree is dropped before the large one is built. The ratio assertion runs only when nextest runs each test in its own process (`NEXTEST_EXECUTION_MODE=process-per-test`), and any other nextest mode fails rather than skips: plain `cargo test` runs the profile tests as threads of one process and their deltas would interleave. Assert `count(2n) ≤ r · (1 + ε) · max(count(n), 64)` for `Linear`, where r is the real growth of the manifest's entries, and `r · ln(2n)/ln(n) · (1 + ε)` for `NLogN`. The load group is killed at 240 s instead of 120 (`.config/nextest.toml`). (`d9ad787`.)
