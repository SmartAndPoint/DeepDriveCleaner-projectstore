# Coverage floor and property tests for the safety invariants

| Field | Value |
|---|---|

| **Status** | in-progress |
| **Priority** | p1 |

## Description

The 561 tests check examples: a given tree gives a given finding. The safety promises hold for any tree, not just the examples, and for those promises examples are the weakest kind of evidence. Coverage is measured (`make coverage`, in CI on every push and nightly), but nothing fails when it drops, and the numbers are wrong: 16 of the 18 test files of `ddc-cli` start the binary with `env_clear()`, which drops `LLVM_PROFILE_FILE`, so the instrumented CLI writes no profile. On `e933b7b` every `ddc-cli/src/cmd/*.rs` and `main.rs` read 0%, `ddc-cli` 48.2%, and the core code those tests run through the CLI is not counted either (`ddc-core` 91.9%).

The promises come from the safety ADR ("Cleanup safety model: risk classes, plan and confirmation") and DDC-001:
- no plan item is a protected folder or a scan root, or an ancestor of one (the ADR protects the folders themselves, not their contents: the children of `Library/Caches` or `.cache` are planned by design); no `user-data` item is planned without explicit selection; no VM directory is planned for deletion or the Trash; no item holds a `.ddc-keep` at any depth or has one in an ancestor inside the scan root; `Library/CloudStorage` and `Mobile Documents` are neither removed nor walked;
- the default selection (ADR §1, §3): no `review` finding is selected by default; a `rebuildable` finding is selected by default only with a known activity signal at its project root or beside it (a manifest, a lock file, `requirements*.txt`, or the git index or `HEAD`; `report/project.rs` `last_activity`, `report/mod.rs` `finding`), that activity older than `min_age`, an environment (a rule with `lockfiles`) only with its lock file (`classify.rs`), and not under `~/Library` or a top-level hidden folder of `$HOME`; a confirmation for some classes runs only the default-selected findings of those classes;
- sizes are counted once;
- the plan does not depend on the walk's thread count or on the order of directory entries;
- an interrupted clean or scan leaves a consistent state.

This story makes the coverage numbers true and sets a floor that only rises, states the invariants as property tests over generated trees, checks the rule matcher against a simple reference, tests interruption, and fuzzes the parsers that read outside input. These tests also guard epic DDC-007's move of the OS calls behind a platform module, so they reach the core through seams that survive it (`DirReader`, `StdReader`, the exec ports), never through `sys::`.

## Decomposition

- [x] Keep the coverage profile through `env_clear()` (`01d980e`): the trait `ddc_loadgen::isolate::ClearEnv` gives `Command` a `clear_env()` that clears the environment and puts back `LLVM_PROFILE_FILE` when the parent has it (a path into the coverage target folder, so the HOME and PATH isolation is unchanged). Every `env_clear()` in `crates/ddc-cli/tests` and `crates/ddc-loadgen/src/measure.rs` goes through it, and `clippy.toml` disallows a bare `Command::env_clear` workspace-wide, so `gate-fast` refuses one. A child killed by a signal writes no profile: lost coverage, not a failure.
- [x] Per-crate floor (`ecfaf68`): `make coverage` (already in CI) also writes `target/coverage/summary.json` and HTML, and `bench/coverage_floor.py` (stdlib, `python3 -I`, tested in `make bench-test`) checks the per-crate and per-file line coverage against `bench/coverage-floor.tsv`, where each of the seven safety files must have a row and a safety file's floor under 90% needs a reason in the TSV. The per-crate floor is set from the CI numbers after the first item minus 1 point, the per-file floors from the lowest of three CI runs minus 3 points (a file such as `exec/guard.rs` branches on the runner's process table and a timed re-read, so a few lines move between runs), never from a local run. CI enforces these floors, not 90%: the 90% target of the next item is reached once, in step 9, recorded in Technical Notes, and then held by the ratchet. `make coverage-ratchet` raises it, run by the owner on `main` from the latest green CI run's summary (`gh run download`), never by CI itself. Lowering a floor is an owner's TSV edit with a reason line (for example a new command the owner keeps manual); CI never lowers it. The floor is checked in CI's `coverage` job and nightly, not in `make gate`, which does not measure coverage.
- [x] Target for the safety path (`c99c8e7`): line coverage ≥ 90% for `exec/mod.rs`, `exec/delete.rs`, `exec/guard.rs`, `exec/preflight.rs`, `exec/journal.rs`, `plan.rs` and `rules/classify.rs`. On `e933b7b`, before the first item: `journal.rs` 71.0%, `delete.rs` 87.5%, `exec/mod.rs` 89.4%, the others 91.4–98.6%. Re-measured after the first item, then tests are added until the target is met, or the reason a line is unreachable is recorded.
- [x] `proptest` strategies for small generated trees (`6a1cf60`, `crates/ddc-loadgen/tests/properties.rs`), the scan root being the generated home (`Env::with_paths`, `roots` naming it), so the protected folders lie inside it: a list of placements (so shrinking drops whole parts) built with `ddc_loadgen::desc` and `fixtures::place`, so a new rule joins the strategy by itself: rule fixtures at a random depth or at home; a marker that matches by a file alone (a valid `CACHEDIR.TAG`, or `pyvenv.cfg`) put directly into a protected folder that the walk asks `Catalog::claimable` about (`Documents`, `Desktop`, `Projects`, `.ssh`, `.gnupg`, `.config`), drawn in at least one case in ten, with nothing else in that folder to block the claim: the folders the visitor descends or claims before asking (`Library`, `Library/Caches`, `.cache`, `.local`, `Downloads`, `Pictures`, `Movies`, `Music`, `Library/CloudStorage`, `Mobile Documents`, `rules/visitor.rs` `before_read` and `after_read`) never reach that check, so a draw among them tests nothing; `.ddc-keep` inside a placement at any depth, or in an ancestor; nested claims; hard links within and across placements; symlinks to protected folders or out of the tree; a VM rule's path with a marker inside; `.git` or a manifest at a would-be finding's top; environments and build products with and without lock files, and ages, for the default selection; rule fixtures under `Library/CloudStorage` and `Mobile Documents`, so that the property about them is not vacuous (a counting reader asserts neither folder is opened). Shrinking is bounded (`max_shrink_time`) so a failing case prints its minimal tree before the `load` group's 240 s kill.
- [x] Property, safety, over findings and plans (`6a1cf60`, `no_plan_holds_a_protected_folder_a_vm_or_a_kept_folder`, `user_data_is_planned_only_as_a_listed_entry_to_the_trash`): for any generated tree, no item of the default plan or of the all-selected plan is a protected folder, a scan root or an ancestor of one; none with action Delete or Trash is at, inside or above a VM rule's path; none holds a `.ddc-keep` at any depth or has one in an ancestor inside the scan root (the entry lock of the user's own folders, ADR amendment 2026-10-20, excepted); no finding, entry or large file lies under `Library/CloudStorage` or `Mobile Documents`; and the default selection of the Description holds over the findings. `build_plan` drops `user-data` findings and the scan roots by construction (`plan.rs`), so those two are not properties of it: the user-data property is over `plan_listed` with a generated list, where a listed user-data folder, an entry with action `delete` or `permanent: true` is refused.
- [x] Property, the executor (`6a1cf60`, `the_executor_refuses_what_the_plan_must_not_hold`; the plan is untrusted input, ADR §1): a protected folder injected into a plan ends skipped with reason `Protected`, not merely skipped; a `Delete` or `Trash` item of a `native-only` rule ends `action-not-allowed`; a listed user-data entry that holds a `.ddc-keep` ends `entry-locked` (ADR amendment 2026-10-20); every removed path lies under a deleted item. An injected protected item must pass the checks before the protected one: inside the roots, not a root itself (so not `$HOME`), complete, with its real `(dev, ino)` from `symlink_metadata` and its parent's real or `None`. The fake `ProcessTable` names `ProcInfo` through a re-export `exec::ProcInfo`, never `ddc_core::sys::`.
- [x] Property, counted once (`6a1cf60`, `sizes_are_counted_once`): `ddc_loadgen::verify::diffs` against the manifest (totals, per-finding bytes and shared bytes, the plan) is empty, and the class totals equal the sum over the non-ignored findings. It runs on the cases `manifest()` models (locks, ages, app-owned downgrades, `user.kept`); a strategy case it does not model (a `.ddc-keep` deep inside a planted finding, nested claims, markers in protected folders) feeds the safety property only, and step 5 lists which ones.
- [x] Property, thread and order independence (`aeb958b`, `crates/ddc-loadgen/tests/order.rs`): a seam `report::scan_with_reader(…, &dyn DirReader)` over the existing `scan_inner`, and a test reader that wraps `StdReader` and permutes each listing by a seed and the directory's path, over one scan root. One thread through `StdReader` and eight threads through the permuting reader (one scan that changes both, since `a265104`) give the same report and plan, with `generated_at` and `duration_ms` left out. The bulk reader is compared to `StdReader` separately, with the private-size fields left out: `StdReader` reads no private size, so `private_bytes` and `selected_reclaimable_bytes` differ for the rules whose files may be clones (the bun, pnpm and uv caches, uv and pnpm environments). Within one root the walk is order-independent by construction (sorted owners, entries, errors; set-based hard-link holders); across roots a hard link's bytes go to the first root seen, so multi-root trees are out of scope.
- [x] Differential test (`b1b4785`): the rule matcher (`RuleVisitor` through the `Visitor` trait) agrees with a deliberately simple reference, a linear scan over the catalog's rules with the documented precedence, on generated paths whose names come from the catalog itself; and whenever the walk claims a rule, `Catalog::verify` agrees.
- [x] Every JSON report round-trips (`bacd408`; `ScanReport`, the clean report, progress lines, the disk report). The ten committed schemas already have drift tests against the types; validating instances needs a validator crate (`jsonschema`), taken only if it passes `make msrv` and `make deny`, otherwise this stays round-trip plus drift and the reason is recorded here.
- [x] Interruption (`1986a29`, `crates/ddc-cli/tests/interrupt_cli.rs`), extending what exists (`scan_cli.rs` SIGTERM of a scan, `clean_items_cli.rs` TERM and HUP during a tool and Ctrl-C, `clean_safety.rs` tombstones): a scan of an S tree killed mid-walk; a clean of every delete item of an S tree with `--json`, sent SIGSTOP after its k-th `item` event, then SIGTERM, then SIGCONT (as `scan_cli.rs` does). An `item` event is written after its outcome and stderr is a buffered pipe, so the clean runs on until the SIGSTOP lands: the test accepts at least k items done, a done prefix and the rest `not-run`, with more than 10·k items so the window stays wide (k + 1 was observed every time: each item fsyncs its journal record) (the clean stops after the current item and re-raises, `cmd/clean_items.rs` and `cmd/clean.rs`); a SIGKILL during one large deletion, where the item is intact, gone or a tombstone that the next scan reports. In each case the lock (`File::try_lock`) is free, `last-scan.json` is the previous or the complete new file, a second run works, nothing outside the plan was removed. A `.last-scan.json.tmp-<pid>` left by a SIGKILL (`store.rs`, nothing sweeps it today) is either allowed or swept, decided in step 8 and asserted by the test. The signal tests are `cfg(unix)` and signal the process group with `libc::kill` directly, not `ddc_core::sys::signals::kill_group`, so the new test files keep off `sys::`; an in-process twin of the SIGTERM case through `ExecOptions.cancel` needs no signals and is the one that runs on every OS. The lists are delete-only: a trash item goes to the real Trash whatever `HOME` is.
- [x] Fuzz targets (`cargo fuzz` in `fuzz/`, the nightly toolchain pinned like the AddressSanitizer run, in the nightly workflow): `disk::plist::parse`, `plan::ListedItems::parse` (the `--items` list), `free::model::ActionList::parse` (the app's `disk free` list), settings (`settings::parse` made public) and the last scan (a `store` function that decodes bytes, split out of `read_last_scan`). `make fuzz` runs each for a set time; a crash becomes a test in `ddc-core/tests/fuzz_regressions.rs`. The parsers of tool output that drive a destructive command are serde_json over the tools' JSON and will not crash; what matters there is semantic, so they get property tests instead of fuzz targets: an orphan set never names a formula with a remaining dependent (`brew/graph.rs` `orphans` and `would_orphan`, read from `brew info`; `free/uninstall.rs`), and a simulator runtime identifier matches exactly one runtime (`free/probe.rs`, `free/simctl.rs`; `simctl runtime delete`).

## Implementation Plan

From `projectstore:planner` (opus), 2026-10-29, on `e933b7b`. Each step is one commit that passes `make gate`.

1. `test: keep the coverage profile through env_clear` (`isolate::ClearEnv`, the 25 call sites, `measure.rs`, the `clippy.toml` rule). Push, read the CI coverage three times (the push, two re-runs) for the per-file spread.
2. `build: per-crate coverage floor`: the `coverage` recipe writes JSON and HTML and runs `bench/coverage_floor.py` (and its test); `coverage-ratchet`; `bench/coverage-floor.tsv` from step 1's CI numbers minus 1; the summary in the `coverage` job's artifact.
3. `test: rule matcher against a linear reference`: `proptest` as a workspace dependency (`default-features = false, features = ["std"]`, passing `make msrv` at 1.89 and `make deny`), `crates/ddc-core/tests/matcher_reference.rs`.
4. `test: no plan holds a protected folder, user data or a VM`: `crates/ddc-loadgen/tests/properties.rs` (the strategy, both halves of the safety property), in the nextest `load` group. In process: `target::Scratch`, `build::build`, `Env::with_paths` with a fixed `now`, `ReaderKind::Std`, a fixed `StatFs` fake, a fake Trash, a fake `ProcessTable` through a new `pub use crate::sys::procs::ProcInfo` in `exec`. The protected lists come through one helper, so DDC-007's per-OS split changes one line. The `brew info` and `simctl` properties go in with the other core properties.
5. `test: sizes are counted once on generated trees` (`verify::diffs`).
6. The `scan_with_reader` seam, then `test: same report for any thread count and entry order`.
7. `test: reports round-trip`, with validation if `jsonschema` passes.
8. `test: interrupted scans and cleans leave a consistent state`: `crates/ddc-cli/tests/interrupt_cli.rs` and the in-process twin in `clean_safety.rs`.
9. `test: safety modules to 90% line coverage`.
10. `ci: fuzz the parsers nightly`: the two public seams, `fuzz/` with its own lock file (checked against `cargo machete`), `make fuzz`, the nightly job, `fuzz_regressions.rs`.
11. The owner's `make coverage-ratchet` on `main`; the seeded-bug run on a throwaway worktree, never committed.

Cases: 256 per property in `make gate`, which CI runs, set in one place (a `gate`-specific `PROPTEST_CASES` that its `nextest` prerequisite inherits); `gate-fast` on its own runs 32, since the pre-commit tier is already over its budget (epic DDC-005: 42 s warm, 78 s after a core change, against 60 s); the nightly raises it. Estimated, not measured: 10–30 ms per case (a tree of about 100 nodes, one to three scans), 3–8 s per property at 256. `jsonschema` goes in with `default-features = false`, since its defaults pull `reqwest`.

## Final Summary

**What changed.**
- The CLI's own code is measured: `ddc-cli/src/cmd/*.rs` runs inside `make coverage`.
- `bench/coverage-floor.tsv` holds per-crate and per-file floors; `bench/coverage_floor.py check` fails the `coverage` job on a drop.
- The safety modules are at or above 90% line coverage.
- Property tests over generated trees: safety, executor, counted-once, order, the brew and simctl parsers. A differential test checks the rule matcher against a simple reference.
- Interruption tests (`interrupt_cli.rs`, and the in-process twin in `clean_safety.rs`).
- Nightly fuzzing of five parsers (`fuzz/`), with the regressions kept as tests. The plist parser got a depth limit after a stack overflow.

**Why.** The safety model (ADR "Cleanup safety model: risk classes, plan and confirmation") rests on invariants that example tests only sample. Epic DDC-007 moves every OS call behind a platform module, and these tests reach the core through seams that survive the move.

**Tests executed.**
- `make gate` before every push.
- Gate runs 40898399504, 40906357001, 40924702851 and 41020282430 (green in all jobs on `8ebe98e`).
- `make fuzz FUZZ_SECONDS=600`: 0 crashes, 2–6 million runs per target.
- Seeded bugs on throwaway worktrees, each caught by a property test (Technical Notes).

**Risks and follow-ups.**
- The interruption scan test raced twice in CI (`6ae225e`, `8ebe98e`; Technical Notes). Both races were in the test, not in the CLI.
- The coverage floors are still `01d980e`'s. Raising them is the owner's `make coverage-ratchet` on `main` (step 11).
- Nightly `PROPTEST_CASES` stays 256. More than about 1500 cases needs a longer job timeout.
