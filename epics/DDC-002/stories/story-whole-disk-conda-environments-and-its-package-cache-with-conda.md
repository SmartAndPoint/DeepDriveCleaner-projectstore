## Description

The owner asked on 2026-10-29 for an action on every Whole disk row that shows a size. The Conda row says "conda clean --all removes the package cache; conda env remove removes an environment" and offers nothing to press. The analysis is in the research note "Removal wherever a size is shown: coding agents, protected folders and the whole disk" (Finding 5).

**Where conda keeps its space.**

- The Conda area (`disk/areas.rs`) covers only `/opt/{miniconda3,anaconda3,miniforge3}`, the all-users installs.
- The installers' default prefix is in the home folder: `~/miniconda3`, `~/anaconda3`, `~/miniforge3`.
- `envs_dirs` and `pkgs_dirs` are empty by default. Conda then uses the first writable location: `<root_prefix>/envs` and `<root_prefix>/pkgs`, then `~/.conda/envs` and `~/.conda/pkgs`. So a user of a root-owned `/opt` install keeps their environments and packages in `~/.conda`, inside the scan roots.
- The catalog has no conda rule, so none of this is a finding today.
- Out of scope: environments created with `-p` anywhere else, and installs elsewhere (`brew install --cask miniconda` under `/opt/homebrew/Caskroom`, the old Anaconda installer's `~/opt/anaconda3`): those keep their environments and packages in their own prefix, which no rule and no area covers. A later story may read candidate prefixes from `~/.conda/environments.txt`.

**The tool.** A finding is cleaned by the conda that owns it, as safety ADR §6 asks ("only if the tool itself reports that path as its own"). The known installs are the three home prefixes and the three `/opt` prefixes, in that order. Each install is asked `bin/conda config --show root_prefix envs_dirs pkgs_dirs allow_softlinks always_softlink --json`: it prints conda's computed settings (the defaults when the config is empty), and conda itself writes nothing for it. It is cheap and deterministic, and the Anaconda Terms of Service plugin, which runs before `env remove`, does not run for `config` or `clean`. (`conda info --json` and `conda env list --json` are not used: both build their `envs` list through `list_all_known_prefixes()`, whose `_clean_environments_txt` rewrites `~/.conda/environments.txt` when an entry is no longer an environment.) A probe that exits non-zero, times out or prints JSON ddc cannot read claims nothing. ddc's runner passes its own environment on, so a `CONDARC` or `CONDA_ENVS_DIRS` set where ddc was started shapes the answer: that is the tool's own view, and accepted. The tool for a finding is the first install whose answer lists, compared by device and inode, the finding's parent in `envs_dirs` (an environment: `envs_dirs` holds the parent folder such as `~/miniconda3/envs`, not each environment) or the finding itself in `pkgs_dirs` (the cache), and whose `root_prefix` is not the finding. Entries that do not exist are skipped. With no such install, an environment takes its fallback and a cache is skipped (below). Every candidate install that exists is asked, at most once per clean, each probe with a 30 s timeout as today's location probes, and its answer is reused for every finding (conda takes seconds to start; up to six starts on a machine with every install); an `/opt` area action's dry run and its run are separate runs and ask separately. The preflight (`clean --items --dry-run`, the sheet's check) never runs conda: it predicts the native command when a candidate `bin/conda` exists, as it predicts every tool today by its presence.

This does not fit today's native command. Go's is a static `program: "go"` found on the tool path (`exec/mod.rs`) with one `LocationProbe` (`crates/ddc-core/src/class.rs`: one program, `Equals` or `Contains` on its stdout). Conda needs a new probe kind: several candidate absolute paths (each through `CommandRunner::at`, never the first `conda` on the tool path), a JSON answer compared by device and inode, and the chosen install's `bin/conda` becoming the command's program, which the journal names. A `{path}` placeholder (the finding's path) joins `{name}` in a native command's arguments and environment values; it never reaches the terminal prompt, which shows the substituted command. A finding path that is not UTF-8 or contains a comma has no native method (a comma would split `CONDA_PKGS_DIRS`, a comma-separated list). The path given to conda, in `-p` and in `CONDA_PKGS_DIRS`, is the firmlinked one (`/opt/miniconda3`, never `/System/Volumes/Data/opt/miniconda3`), so conda's own string comparison with its `root_prefix` stays a second refusal of the base, and the command the sheet shows is the one a person would type.

**Scoping each command to one folder.** `conda clean` cleans every package folder it can write, so with a home install's `pkgs` and `~/.conda/pkgs` both present, one command would empty both. Every `conda clean` therefore runs with `CONDA_PKGS_DIRS=<that one folder>` in its environment, and never with `--force-pkgs-dirs`. The variable alone does not bound it: `pkgs_dirs` is a sequence setting, and conda merges a sequence from every source (the variable first, then each `.condarc`), so with a `.condarc` that lists two package folders the command would still clean both. So the scope is verified, not assumed: right before each clean and its dry run, the claiming install is asked `conda config --show pkgs_dirs --json` with the same `CONDA_PKGS_DIRS`; entries that do not exist are dropped (conda's clean drops them too), and the clean runs only when what remains is exactly one folder and it is the finding, by device and inode. A second existing folder skips, writable or not (ddc does not imitate conda's own writability test); otherwise the cache is skipped as `tool-not-ready` ("conda's package folders are set in a .condarc and cannot be limited to this one"). It runs as `conda clean --index-cache --packages --tarballs --logfiles --yes`, never `--all`, `--tempfiles` or `-c`: those also walk the whole install of the conda that runs (`find_tempfiles` walks `sys.prefix` when given no path), which `CONDA_PKGS_DIRS` does not bound. The four flags act on `<folder>`, `<folder>/cache` and `<folder>/.logs` only. On conda 26.9 and later, `--packages` also lists environments to find softlinked packages, which may rewrite `~/.conda/environments.txt`, the same as `env remove`. `conda env remove -p <path> --yes` names its one environment, never `-n`/`--name`, never the base. It also rewrites `~/.conda/environments.txt`, outside the finding, and releases before 24.9 remove the `envs` folder, and its empty parents, when it is left empty: the safety ADR amendment admits both. On an Anaconda Distribution install, the Terms of Service plugin runs before `env remove`; with stdin closed a user who never accepted the Terms gets a failed action carrying the plugin's message, and nothing is removed. `env remove` runs conda's unlink transaction before it deletes the folder, so a package's pre-unlink script may run: accepted, as it would in Terminal.

**Two parts, one tool.**

1. **In the home folder: catalog rules with a native method**, as the catalog already has for Go and others (`native` in `catalog.rs`):
   - `python.conda-env` (the id follows `python.venv`): a folder with `conda-meta/history` under `miniconda3/envs`, `anaconda3/envs`, `miniforge3/envs` or `.conda/envs` in the home folder. Review class, category `Toolchain`. Method: `conda env remove -p {path} --yes`. Fallback: Trash. Group: "Python environments". Never an install's prefix itself (the base environment): the matcher matches only children of an `envs` folder, and the probe refuses a finding equal to `root_prefix`. Today's matchers cannot say "a child holding this file" (`KnownChildren` cannot test for `conda-meta/history`, and the rules test forbids `Scope::Item` on it), so the rule needs a new `Matcher` variant.
   - `cache.conda` (the id follows `cache.uv`): `miniconda3/pkgs`, `anaconda3/pkgs`, `miniforge3/pkgs`, `.conda/pkgs` in the home folder. Safe class, category `PackageCache`. Method: `conda clean --index-cache --packages --tarballs --logfiles --yes` with `CONDA_PKGS_DIRS={path}`. No fallback: when no conda claims the folder, the finding is skipped as `tool-not-ready` ("no conda lists this folder"), a skip reason the clean report already has. Deleting or trashing the folder is not safe without conda: with `allow_softlinks` or `always_softlink` the environments' files are symlinks into `pkgs`, and removing it breaks them. This needs a new `Fallback::Skip`, internal to the core: the first native rule whose fallback is a skip. For the same reason, when any install whose `pkgs_dirs` lists the cache answers `allow_softlinks` or `always_softlink` true (`~/.conda/pkgs` is in every install's list, so an `/opt` install's environment may link into it), the cache is skipped as `tool-not-ready` ("conda links packages into environments by symlink") and no command runs: before 26.9 `--packages` decides "unused" by the hard-link count alone, so a softlinked package counts as unused and is deleted. Both settings are off by default. On 26.9 and later conda checks softlinks itself, but only for environments listed in `environments.txt`; the skip stays. Accepted, as conda in Terminal does the same: a package softlinked while one of the settings was on, which is off now, counts as unused on conda before 26.9. Group: "Package downloads". The confirmation shows its hint, "Removes unused packages only: packages environments use stay, so less may be freed than the folder's size"; today `CleanWording` shows a hint only for the Review class, so the app learns to show it for this rule. After the clean, the existing re-measure of tool-cleaned findings reports what was really freed.
   - Each gets the plan, the re-check, the in-use check of safety ADR §5 (a running process whose `CONDA_PREFIX` is the environment, which `ProcInfo.env_prefixes` and `exec/guard.rs` already count for a native action: this part needs a test, not code), and the journal of every finding.
2. **In /opt: area actions through `ddc disk free`**, in the sheet that runs `brew cleanup` today (story "Whole disk: free space with the owning tool"):
   - `ddc disk` lists each `/opt` install's environments from the file system, not from conda: every `<prefix>/envs/*` holding `conda-meta/history`, and the install's `<prefix>/pkgs` with its size and whether the user can write it. An environment's files are hard links into `pkgs` (conda's default on one volume, and an install's `envs` and `pkgs` are always on one volume), so removing an environment frees only what is not also in the cache. The install is walked once, each environment and `pkgs` as its own region, so a file linked in both is counted in `shared_bytes` (as the disk walk already counts a file two owners hold): an environment row shows its bytes and "N also held elsewhere, such as the package cache" (the walk cannot say where a file's other link is). `ddc disk` never runs conda: it only measures (the structure test `the_disk_report_never_reaches_cleanup`, menu bar ADR §6 item 10). The disk report gains an optional `conda` section, as it has `simulators`;
   - the Whole disk view shows each environment as a row nested under the Conda row, with its size and its own Remove Environment… offer, as simulator runtimes are shown today; the Conda row offers Clean Package Cache…. One environment per sheet: the one-offer sheet is reused as it is. Several at once is the p3 story "Whole disk: free the checked areas in one sheet";
   - when `<prefix>/pkgs` is not writable for the user, the Conda row offers no cache action and says the user's packages live in `~/.conda/pkgs`, a `cache.conda` finding in the Review window;
   - two actions: `conda-env-remove` (identifier: the environment's path) and `conda-clean` (identifier: the install's prefix). Each runs after a dry run: for an environment, its own bytes (files whose every link lies inside it); for the cache, `conda clean --index-cache --packages --tarballs --logfiles --dry-run --json` (with the same `CONDA_PKGS_DIRS`), whose estimate is the sum of `packages.total_size` and `tarballs.total_size` (the index cache and the logs are listed as bare paths; ddc does not count them). It prints the JSON and then exits 0 through `DryRunExit`; ddc reads the first JSON document and ignores anything after it. The environment is measured as one region of a walk, and only its own bytes count: the walker already counts in a region's `bytes` only the files whose every link lies inside it. That is the dry run's estimate and the bytes before; after the run the folder is walked again. So a link into `pkgs`, into a package folder a `.condarc` put elsewhere, or into another environment is never reported as freed, and the measure needs no other folder and no care for how a path is spelled. `free/measure.rs` gains that measure: today it returns a walk's `total_bytes`; the sheet says the rest is freed by Clean Package Cache;
   - the probe asks the install as above and refuses, each with its own refusal: a prefix that is not one of the three `/opt` prefixes (by device and inode); an install whose `root_prefix` is not that prefix; an environment whose parent is not in `envs_dirs`, that lacks `conda-meta/history`, that is the base, or that is in the home folder (that one is the catalog rule's); a cache folder not in `pkgs_dirs`; an environment a running process uses. `FreeContext` gains the process table for that last check, reusing `exec/guard.rs`;
   - a root-owned install is refused by the probe before conda starts, with its own refusal and the administrator wording: an environment, or `<prefix>/pkgs`, that the user cannot write. conda would not say so in words ddc recognises (it refuses with "operations have been disabled on your system" or a write-permission error), and in two cases it exits 0 having done nothing: an environment with no package records goes straight to a delete that swallows its failure, and a clean whose package folder is not writable finds nothing to clean. For the same reason, an environment still present after conda exits 0 is reported as removed but not freed, never as freed, and stays in `last-disk.json`; the catalog's `python.conda-env` reports it as failed. Never `sudo`;
   - the exclusive data-dir lock and an `area-action` journal line, as for `brew cleanup`; after an environment's removal, `last-disk.json` drops it from the `conda` section, and after either action it marks the Conda area stale. The path given to conda is built from the probe's answer: the matched `root_prefix` joined with `envs/<name>` for an environment, `root_prefix` and `pkgs` for the cache;
   - with more than one `/opt` install, each install is a row nested under Conda with its own Clean Package Cache… offer, and its environments nested under it;
   - `ddc disk free` at a terminal offers both actions like the others, which starts each `/opt` install's conda for its dry run.
   - A clean of the cache can race a `conda install` writing into the same folder, as it would in Terminal: accepted.

**Schemas.** The two action ids join `ActionId`, shared by the disk report and the `--actions` list, and the probe's refusals join `Refusal`; the app decodes both strictly. So `DISK_SCHEMA_VERSION` and `FREE_SCHEMA_VERSION` both go from 1 to 2, the schemas are regenerated (`--test disk` and `--test disk_free` with `DDC_UPDATE_SCHEMA=1`), and DDCKit's contract tests and fixture follow. The story "Whole disk: Homebrew packages, their sizes, and brew uninstall" bumps the free schema and extends the same `ListedAction`: whichever lands second builds on the other's version, and one release carries one bump of each. The scan report gains no field: the rules use existing categories. The journal's `area-action` line carries the new ids in `action`; the journal has no published schema and no reader in ddc or the app, so `JOURNAL_SCHEMA_VERSION` stays 3, and a reader of `actions.jsonl` must accept an action id it does not know.

**Before it starts (the work-start gate).**

- A safety ADR §6 amendment, critic-reviewed: the tool lookup above (candidates, the `config --show` answer, device and inode, first install wins, the `root_prefix` refusal); `conda env remove` and `conda clean` rewriting `environments.txt` outside the finding, and older releases removing an empty `envs`; `conda clean` limited to its four flags and scoped by `CONDA_PKGS_DIRS` with the comma rule; `cache.conda` skipped, never deleted, without its conda or when conda softlinks; the `/opt` environment measured alone, its own bytes only (every link inside it); the scope of every `conda clean` verified by asking conda; the area action refusing home folders; the in-use check on the /opt path; and both schema bumps.
- The structure test `disk_free_runs_only_its_two_commands` is a list of forbidden substrings in `free/`, comments included (`Command::new`, `remove_`, `sudo`, `autoremove` and others). The conda commands pass it as it stands, so it is renamed and gains positive checks: `env remove` only with `-p`; `clean` only with its four flags; never `--force-pkgs-dirs`, `--all`, `--tempfiles`, `-n`, `--name` or `base`; and conda is never looked up on the tool path (`commands.find("conda")`). Function names with `remove_` stay out of `free/`.
- The story "Whole disk: free the checked areas in one sheet" (p3) assumes only runtimes and Homebrew can free anything. This story amends it: an `/opt` install's cache and environments join the rows that can be checked.
- "Whole disk: free space with the owning tool" has shipped its code (`ddc disk free`, the action sheet, the probe pattern); what keeps it in progress is its manual checks by the owner. This story builds on that code and does not wait for those checks.

## ## Final Summary

## Deviations at implementation

- `ddc disk` measures the /opt conda section with a second walk of its own, not as regions of the Conda area's walk, so the Conda area's numbers stay as they were.
- The home preflight never runs conda (as the body and the ADR say), so its dry run cannot predict a not-scoped or softlink skip; AC 3's "dry run included" holds for /opt only.
- This story takes free schema version 2; the Homebrew packages story builds on it (2 to 3).
- Open, low: the CLI's interactive prompt for the conda actions has no test (it needs a terminal); no test of a cache path with a comma, nor of an /opt clean under a `/System/Volumes/Data` identifier; two types are named `CondaFolder`.

## Technical Notes

- Tests never run a real conda: a script in a temp folder stands in for `bin/conda`.
- `~/.conda/pkgs` is also in a home install's `pkgs_dirs`; the home-first order decides which conda cleans it, and a test pins that order.
- `free/`'s structure test does not strip comments: a comment there must not say "trash", "prune", "sudo" or "remove_". `disk/` forbids the quoted string `"delete"`, `remove_` and `plan::`.
- The catalog's `rule_fixture` panics on a rule with no fixture, and `tests/rules.rs` and `tests/recheck.rs` iterate every rule.
